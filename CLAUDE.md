# CLAUDE.md — Vanguard AI-Enabled Sell & Rebalance

## 0. How to use this file

This is the single living context artifact for this project. Read it in full before any planning or build task — it replaces the four-file, phase-split structure (`pm/`, `pd/`, `dev/`, root) used in the original Vanguard Sell & Rebalance pipeline project. That structure does not carry forward here; this project deliberately does not use sequential PM→PD→Dev phases.

**Standing rule — read this before every session, follow it at the end of every session:** roles (PM/PD/Dev) persist as jurisdiction over judgment, not as sequential phases. Work whatever section of this project needs attention next; there is no gate requiring one role's pass to finish before another's begins, except where a decision is genuinely dependent on an earlier one (e.g., you cannot write a boundary rule for a feature that hasn't been scoped). When a decision is made, log it in `DECISIONS.md` immediately, tagged with the role-lens that produced it (PM/PD/Dev), **before ending the session** — a session that ends without that write is exactly how context got lost in the predecessor project (manual copy-paste between Claude Chat and Claude Code, occasionally skipped to save credits). This file and `DECISIONS.md` are the entire mechanism that replaces that relay. If they're not kept current, the mechanism doesn't work, regardless of which tool you're in.

**Standing rule — regenerate `docs/progress.html` at natural checkpoints**, not every session: a feature completed, or a significant multi-session block of work finished. Regenerating means re-reading `CLAUDE.md` and `DECISIONS.md` fresh and re-writing the summary from their current content — never hand-patching the old version. This page is the human-facing status view (see D050); it goes stale exactly the way everything else in this project has before someone thought to check, so treat it as part of closing out a checkpoint, the same way logging a decision is part of closing out a session.

**Standing engagement expectations** (generalized from the market-data session — see `DECISIONS.md` D033–D037 for where these came from):
- Before editing any value that other computed fields, tests, or UI locations might derive from, check for cascading dependencies first — don't assume a field is isolated.
- When a problem seems to present exactly two options, treat that as worth a second look rather than a given — check whether a third option avoids a real cost that both original options share.
- Prefer surfacing an assumption or an unresolved tradeoff explicitly over resolving it silently in whichever direction is easiest to implement.

## 1. Project relationship and scope

This project adds an embedded AI interpretive/generative layer to the **Vanguard Sell & Rebalance** application, which was fully built, deployed, and documented in a separate, prior, now-untouched portfolio project (a three-role PM/PD/Dev pipeline across Notion/Jira/GitHub/Figma). That original project's repository remains the complete historical record and is not modified or referenced from within this repo — no cross-repo links belong in this file. (The relationship between the two projects is described externally, in portfolio/case-study materials, not here.)

This project's primary objective is learning to design AI-**enabled** applications — extending an existing, deployed application (Vanguard Sell & Rebalance, a separate, prior, now-untouched portfolio project) with AI capabilities that extend the *user's* capabilities. This is a distinct category from that prior project's focus, which was AI-**assisted** design and development — using AI tools to accelerate building an application and demonstrating capability across multiple simulated roles (PM/PD/Dev). That project put AI inside the *process* for the builder; this one puts AI inside the *product* for the end user.

A secondary, coincidental learning track emerged during this project: consolidating context into one continuously-updated file pair (this file and DECISIONS.md) instead of a phase-gated, multi-system handoff structure, testing whether PM/PD/Dev role-based rigor persists without sequential relay. This is real and documented throughout this file and the decision log, but it is not the project's primary purpose — the AI-enabled features (§7, §8) are the actual subject; the process is the means of executing them legibly, not the point of the exercise.

**Scope — two features, not four to five:**
1. **AI narration layer** — one cross-cutting capability applied at four existing static-text touchpoints (Fund Selection rationale, Scenario Analysis tradeoff summary, Order Confirmation summary, Execution Summary narrative). Upgrades an existing deterministic string to an AI-generated one at each location; introduces no new UI surface.
2. **AI-assisted "what-if" exploration** — a collapsible AI assistant panel in Scenario Analysis that interprets natural-language requests, clarifies ambiguity, and — after human confirmation — constructs or modifies a scenario by calling the existing calculation engine directly, without requiring navigation to Fund Selection.

**Rejected candidates** (see `DECISIONS.md` D004 for full reasoning): voice/chat-based Order Confirmation entry (wrong risk/value ratio at the highest-stakes, currently input-free stage); document ingestion for holdings extraction (violates bottom-up data construction, no UI precedent, high hallucination risk).

**Standing principle — genuine generation, not simulation** (project-wide, governs both features, not just Feature 1 — see `DECISIONS.md` D038, D042): All "AI-generated" or "AI-assisted" content in this application must be produced by an actual call to a language model at runtime, via a swappable generator interface — never templating, deterministic string assembly, or any other simulated mechanism, regardless of implementation convenience or infrastructure cost. The provider behind that interface is changeable without redesigning calling code, tests, or the fallback logic — **the current active default provider is Gemini** (`gemini-3.5-flash-lite`, via Google AI Studio — D042 originally picked `gemini-2.5-flash-lite`, retired for new API keys shortly after, see D043), with Anthropic (`claude-sonnet-5`) and Groq (`openai/gpt-oss-120b`, D065 — chosen after the originally-planned `llama-3.3-70b-versatile` turned out not to exist in this account's real model catalog at all) as two further working, available-but-not-default adapters, switchable via the `NARRATION_PROVIDER`/`WHATIF_PROVIDER` env vars. D038 named Anthropic specifically before this generalization; D042 is the refinement, not a reversal of "real model call, never simulated." D065's own finding, stated plainly there: Groq transferred every tested boundary rule correctly and had flawless structured-output parsing, but isn't "proven equivalent" to Gemini yet — available, not preferred, same status Anthropic already had.

- SpecID selection: sell-amount field becomes read-only and the lot-detail panel reveals, atomically, on method selection. This is a **business rule** (SpecID is only valid once specific lots are resolved) independent of which UI surface enforces it — the chat-based assistant must reach the same fully-specified state before it can call the engine, even though it won't replicate the exact field-lock/panel-reveal UI mechanism.
- Wait & Save is suppressed entirely in Automated mode; appears only in Manual mode / manually-active fund rows.
- **`selectFundsAutomated()`'s target-fill has 4 phases, not 3 — a single-holding (or fully-drift-concentrated) account needs Phase 4 to fully fill the requested amount** (D059). Phases 1–2 split the target into an allocation budget (60%/70%) and a loss-harvest budget, each spent on a *different* holding; Phase 3 tops up from any holding *not yet touched*. An account whose only qualifying holding was already claimed by Phase 1 or 2 has nothing left for Phase 3 to draw from, so the unspent budget fraction silently vanishes from the recommendation — reproduced live: Roth IRA holding only VFIAX, $25,000 tax-first request, sold only $15,000 (the 60% allocBudget) with the other $10,000 unaccounted for, no error or warning. Phase 4 revisits already-selected holdings (up to `current_balance`) when Phase 3 leaves a shortfall and no untouched holding remains. Any future change to the phase-budget split must preserve this — a target-fill routine that partitions a total across categories needs an explicit "nothing left to draw from" fallback, not an assumption that some other, untouched holding will always exist.
- **Manual-session state (`manualActiveFundIds`/`manualAppliedAmountsCents`/`manualCostBasisMethods`/`manualLotSelections`) is keyed by fund_id alone and must be cleared whenever the active account changes, from any call site** (D059, extending D057's original but incomplete guard). This is now enforced centrally in `setActiveAccountId()` itself (`dev/src/store/useAppStore.ts`), not by individual pages remembering to call `clearManualSession()` — D057 added that call only to `FundSelectionManual2.tsx`'s own account-switch handler, so switching accounts from `FundSelectionAutomated.tsx` left a stale, now-mismatched manual session in the store that silently broke the *next* Manual-mode visit (the engine couldn't find the leftover fund_ids in the new account's holdings, producing an empty result with no error). Treat account-scoped session state as something the account-id setter itself must own clearing, not something each new switching UI has to independently remember.
- **A memoized callback bound to `useAppStore()` values is stale within the same synchronous function that just called a store setter — a store update doesn't force a fresh re-render (and thus a freshly-bound callback) until after that function returns** (D060). `FundSelectionManual2.tsx`'s `switchAccount()` called `setActiveAccountId(accountId)` then immediately invoked `runManualEngine()` (a `useCallback` closing over `activeAccountId`) — that callback still held the *old* account id, so it silently looked the new account's fund_ids up in the wrong account's holdings and produced an empty result. Fixed by calling `runOptimization()` directly with the new account id passed explicitly as a parameter, not by routing through a memoized callback that assumes the store has already caught up. Any handler that changes `activeAccountId` and then needs to act on the *new* account in the same tick must pass the new id explicitly — never rely on a callback whose closure reads it back from the store.
- **Effects guarded to "skip the first render because a sibling effect already covered it" are only as correct as that sibling's own condition — verify the assumption holds when the component mounts in a non-fresh state, not just on first-ever app load** (D060). `FundSelectionAutomated.tsx` had a mount-only effect (`!recommendation` guard) and a separate account-change effect that unconditionally skipped its own first invocation. This is correct only when `recommendation` is genuinely absent on mount; if the component remounts with a *stale* `recommendation` left from a different account (e.g., the account changed while a different page was showing), neither effect recomputes — and this was invisible in this project's own dev environment specifically because React 18 StrictMode double-invokes mount effects, and the skip-guard ref gets flipped by its own first (discarded) invocation, so the second invocation happens to fire and recompute correctly. That masking is dev-only; a production build has no such rescue. Fixed by collapsing to one effect keyed only on `[activeAccountId]` with no skip-guard, so it always recomputes on mount and on every change alike — correctness must not depend on StrictMode's double-invoke behavior working in your favor.
- **Any function that restores session state from a saved object (a scenario, a transaction) must restore `activeAccountId` too, not just the dollar amounts and mode** (D061). `startEditingScenario()` in `dev/src/store/useAppStore.ts` restored `targetSaleAmount`, `mode`, and the full manual-session shape from the clicked scenario, but left `activeAccountId` untouched — so editing a scenario built against a different account than whatever was currently active showed a freshly-recomputed, completely wrong-account recommendation for the scenario's dollar total, not the scenario's actual data. Fixed by setting `activeAccountId: scenario.account_id ?? DEFAULT_ACTIVE_ACCOUNT` in both branches (the fallback covers only pre-D057 scenarios, which are genuinely taxable-only). Any future "restore this saved state" function needs the same account-id restoration, not just whatever fields happen to differ between automated/manual mode.
- **MinTax lot selection minimizes total tax *dollars*, not tax *rate*** (`selectLots()` in `dev/src/engine/index.ts`, sorts by `(nav - basis) / nav * taxRate(holding_period)` ascending). This means a recently-acquired short-term lot with a high cost basis relative to current NAV (small embedded gain, taxed at the higher ST rate) can legitimately beat an old long-term lot with a large embedded gain (taxed at the lower LT rate) — the small-gain lot's low absolute tax can undercut the large-gain lot's rate advantage. Verified directly against the real engine for VTSAX's actual lots (a $5,000 sale): the ST lot MinTax picks produces $105.78 in tax, genuinely the lowest of all 9 real alternatives — the next best (an LT lot) produces $143.75, and the largest embedded-gain LT lots produce $500+ despite the lower rate. Correct-but-counterintuitive behavior — documented here specifically so it isn't re-flagged as a suspected bug (see `DECISIONS.md` D046).

## 7. AI/code boundary spec — Feature 1 (narration layer)

- Pure explanation. The AI may only describe values the engine has already computed; it may never state, estimate, or imply a figure itself.
- Every generated block must respect the EST. TAX / EST. NET TAX distinction exactly as computed.
- Applies identically at all four touchpoints — one spec, four call sites, not four bespoke specs.
- Disclosure per CD-1.2 required at each touchpoint (visually distinct from static/deterministic text) — **only when the content shown actually came from the model.** See fallback rule below for the case where it didn't.
- **Tense is per-touchpoint, not a global default (D062)**: Fund Selection rationale, Scenario Analysis tradeoff summary, and Order Confirmation summary all narrate a **proposed, unexecuted** plan — none of these three has actually sold anything yet — and must use a proposed/conditional frame ("Selling $X would realize...", never "Sold $X..."). Only Execution Summary narrative describes something that has actually happened, and is the sole touchpoint that should read in the past tense. `NarrationInput.tense` (`'prospective' | 'past'`) already carried this distinction correctly per touchpoint in `narrationBuilders.ts`, but `dev/src/server/narrationPrompt.ts` silently discarded the field and never told the model about it — the model defaulted to declarative past tense everywhere, including the three touchpoints that haven't executed. Fixed by wiring `input.tense` into an explicit `TENSE_INSTRUCTION` in the system prompt. Any new touchpoint added in the future must set `tense` deliberately (prospective unless it is genuinely post-execution) — do not assume the default is safe.

**Narration engine architecture** (see `DECISIONS.md` D038, D042):
- Generation is a real LLM API call at runtime, per §1's standing principle — not templating or deterministic assembly — made through a provider-agnostic `NarrationGenerator` interface so the active provider is swappable without touching the fallback logic, the caching layer, or any touchpoint call site. Implemented as a minimal Vercel serverless function, `dev/api/narrate.ts`, wrapping shared core logic also used for local dev-server parity and for direct unit testing.
- **Provider-agnostic by design (D042)**: `getActiveGenerator()` selects Gemini (default) or Anthropic via `NARRATION_PROVIDER`. Both adapters build their prompt from the same shared, provider-agnostic prompt content (`dev/src/server/narrationPrompt.ts`) — no prompt text is duplicated per provider.
- **Input/output contract is the CD-4.2 boundary made architectural, not just conventional**: the function receives only already-engine-computed structured figures (fund/lot identifiers, amounts, gain/loss figures, tax figures, allocation deltas, flags, and — when not excluded — the market-context figure). It never receives raw account data and never performs any calculation. It returns prose text only. **Test/review-tooling fixtures must build these figures by calling the real engine (`runOptimization()`), never by hand-constructing them with guessed defaults** — an earlier version of both the test suite and the review-sample script did the latter and silently zeroed every tax figure; see D044.
- **Prompt-quality rules** (`dev/src/server/narrationPrompt.ts`, see `DECISIONS.md` D045, D047): explicit dollar/share/percent formatting; **`effective_rate`, when present, is explicitly framed as already being a percentage number (D119)** — added after a live-observed misread of a genuine sub-1 percentage value (`0.26`) as a fraction needing its own ×100 ("about 26%"), found while verifying D119's actual root-cause fix (a real unit mismatch between the fraction `Recommendation`/`SavedScenario` store internally and the real percentage `TransactionRecord` stores — narration now always receives a true percentage regardless of source, this instruction is a secondary defensive clarification on top of that data fix, not a substitute for it); the market-context figure must be framed as the fund's trailing-12-month return as of a fixed reference date, never as lot-specific ("since you bought it"); natural-language phrasing, never a field's internal name, and uninformative zero-figures omitted (except a $0 tax caused by IRA/Roth account type, which is meaningful and must be stated); Traditional IRA lines must state what's actually taxed (the withdrawal, as ordinary income) **and, since D083 made it a real number, the actual dollar tax figure itself (`est_net_tax`)** — not just the qualitative rule on its own; segment tone is structured by rule, not just length — segment A scales to one short sentence *per fund* for multi-fund transactions, not one sentence total regardless of fund count. **Segment D's "orientation before specifics" rule (D112) now says so explicitly, and cites the real research field for it** — `SEGMENT_PROFILES.D.toolMust` ("Orientation before action...") existed in `segmentResearch.ts` since D074 but was never actually interpolated into `SEGMENT_TONE.D`, only `.goal`/`.toolMustAvoid` were; the prompt's own softer "acknowledge the outcome before explaining it" wording let the model satisfy it while still opening with the dollar figure. Real generated output (read cold) showed this playing out inconsistently across touchpoints from the one shared instruction — correct at Scenario Analysis/Order Confirmation, absent at Fund Selection's per-fund rows and at Execution Summary — not from duplicated, drifted copies (`SEGMENT_TONE[input.segment]` is referenced identically by all four touchpoints). Fixed with an explicit first-sentence rule plus a prospective and a past-tense example opening, since Execution Summary's own gap was plausibly reinforced by the past-tense instruction's own "Sold $X..." example with nothing to counter it. **That single example sentence per tense itself turned out to be a second problem (D113), caught by re-checking against genuinely different transactions rather than trusting D112's own three-example review**: the model was echoing the example's specific wording almost verbatim across unrelated transactions (7 of 8 real prospective-tense outputs collected across both decisions were close paraphrases of one sentence), not just following its structural pattern. Fixed by replacing the one canonical example per tense with two deliberately differently-worded ones, explicitly labeled as illustrative rather than a template to copy, plus an explicit instruction to vary wording — re-verified with six more real calls (three new transactions plus a re-run of D112's own fixture) all still orienting correctly, now with genuinely varied phrasing. **Segment C had the identical example-anchoring defect (D123), never checked at the time D113 fixed it for Segment D**: its one quoted example's figures matched this project's own canonical test scenario exactly, so a live call for that scenario reproduced the example byte-for-byte, and 4 of 5 calls against genuinely different transactions still echoed its exact phrase. Unlike D113, adding more examples (two, then three) only anchored harder or shifted which fixed template got echoed — the fix that actually worked removes quoted example sentences from `SEGMENT_TONE.C` entirely, replaced by an abstract "state the tax figure first, stop immediately after the amount, vary the shape each time" rule with nothing left to copy verbatim. Content-rule compliance (no ST/LT breakdown, no allocation mention) had to be re-verified alongside this, not assumed to carry over automatically — an earlier no-example attempt fixed wording variety but broke compliance (the model filled the space with a banned qualitative allocation clause once it had no example modeling that clause's absence).
- **Early-withdrawal-penalty narration is omit-by-default, not a permanent disclaimer** (`NarrationInput.est_early_withdrawal_penalty`, see DECISIONS.md's IRA narration entry): mentioned only when a real, nonzero figure is present — the `'not_applicable'` sentinel (today's only real value, per D083/note_retirement_status) and a genuine `$0` are both coerced to `undefined` at the `narrationBuilders.ts` boundary (`meaningfulPenalty()`) before the figure ever reaches the prompt, never passed through and instructed away. This means the field is never actually threaded through `ManualConfiguration`/`SavedScenario`/`TransactionRecord` (only `Recommendation` carries it, per D083/D085) — Manual/Scenario/Execution-sourced narration simply never has the field to omit in the first place, which produces the identical (correct) "say nothing" behavior without needing the field added everywhere. The moment this assumption changes (a real, computed, nonzero penalty), narration starts stating it automatically — no separate flag to remember to flip.
- **Tests mock at the interface/HTTP boundary, not any specific provider's SDK or endpoint.** Same precedent as the market-data rules below (no live network dependency in tests) — not a separate decision, the same one applied to every live-data source. This is also what makes the provider swap safe: client/caching tests mock `fetch` against `/api/narrate` (provider-agnostic already), and adapter-selection tests assert on `getActiveGenerator().name`, never on which HTTP call happened underneath.
- **Failure fallback differs from the market-data sentence's rule on purpose.** Market context is supplementary — omitting it silently on failure is fine (rule 2 below). Narration is the *primary* content at all four touchpoints, so on API failure the touchpoint falls back to a plain, deterministic summary of the same structured figures rather than blank space. That fallback **must not** carry the CD-1.2 AI-generated badge — it genuinely isn't AI-generated in that state, so the badge stays honest in both the success and failure case rather than becoming a fixed label that's sometimes false.
- **Caching**: narration is memoized client-side by a stable hash of the full input payload (touchpoint + structured figures, including market-context/exclusion state) for the session. Decided explicitly, not a silent default — see D038 for the reasoning. Cache keys don't include which provider generated the text — see D042 for why that's fine (the fallback/interface boundary the client depends on doesn't change across providers).
- **Market-data rules** (governs the third narration input, live market-performance context — see `DECISIONS.md` D028–D031, D037):
  1. May state only a percentage return between two real dates — never an absolute price, real or fictional, in the same sentence or surrounding narration.
  2. The figure is a static, precomputed dataset value verified once at authoring time, never a live runtime fetch — no failure-handling or test-mocking logic is needed for it as a result.
  3. **Never fabricate or overwrite a verified real figure to force agreement with the fictional dataset, and never adjust a fictional value without first checking for cascading dependencies** (other display locations, self-consistency/rollup fields — see `DECISIONS.md` D036 for what that check looks like). When a genuine real-vs-fictional conflict is found for a specific fund/lot pairing: if the fictional side can be adjusted safely (no cascading dependents), adjust it and document the change in `note_market_data`, following the precedent of the existing `note_investor_age` field. If it can't be adjusted safely, add an entry to `dataset_metadata.market_context_exclusions` (fund, lot_id, reason) instead and suppress the narration for that specific pairing — the real figure stays as-fetched, the fictional side stays untouched, and the conflict is documented, not resolved silently either way.

## 8. AI/code boundary spec — Feature 2 (what-if assistant)

- **Human-in-the-loop stages are interpretation, not calculation**: prompt → interpret → clarify (if underspecified) → present plain-language interpretation → user confirms → *only then* call the engine. This is the direct instantiation of the original project's "human-in-the-loop labeling throughout" principle, applied for the first time to a real feature.
- **No preview-with-numbers step exists between confirmation and computation.** What's shown pre-compute is the interpreted intent in plain language (e.g., "reduce VTSAX by $5,000, increase VBTLX by $5,000") — not a numeric result, since no numeric result exists yet at that point.
- **The assistant is treated as an external edit tool, equivalent to a Fund Selection round-trip** — not a shortcut around the complexity that made Scenario Analysis read-only in the first place (that complexity was specifically SpecID/cost-lot selection; confirmed via project design history, not inferred). The assistant must reach the same fully-specified state Manual mode requires (see §5) before any engine call — no exemption for being conversational.
- **Capability model: one slot-filling interpret/clarify/confirm loop, not four separate builds.** Simple delta, new comparative scenario from a base, full specification, and iterative multi-turn clarification (including inline lot-level detail, e.g. for SpecID) are all the same mechanism exercised at different levels of user-supplied detail — design and build it once, let it degrade gracefully to asking for whatever is missing.
- **Direct engine invocation, bypassing the Fund Selection screen, is architecturally sound** — the engine is a standalone module (§2), not embedded in the Fund Selection component, so the assistant calling it directly does not duplicate or risk diverging from Fund Selection's own calls, *provided* the assistant only ever calls the shared engine module and never reimplements any calculation or business rule itself. If the assistant pathway and the Fund Selection pathway ever produce different numbers for identical inputs, that is a defect in the assistant's integration, not a second valid answer.
- **Scenario provenance and mode tagging**: any scenario the assistant creates or modifies gets the "AI-assisted" badge (§3), independent of whether the resulting scenario is fund-specific (pairs with the "Custom" badge — not absence of a badge, see §3/D040) or objective-driven (pairs with "System recommendation — [priority]", where priority maps to the Tax-first/Balance-first toggle the prompt implied or specified). **Resolved (D056), no longer open:** one pill, compound text — the existing badge's text switches to "AI-assisted — Custom" or "AI-assisted — [priority] optimized," not two adjacent badges. There is no precedent anywhere in this design system for stacking two badges together, and the glossary's own illustrative examples (§3) are single compound phrases — the pill's existing color (gray for Custom, teal for System-recommendation) still signals which case it is.
- **This is a deliberate scope increase over a lighter "delta + redirect to Fund Selection" design that was considered and superseded** — chosen because the project's goal is depth of embedded-AI expertise for a case study, not least-cost delivery. See `DECISIONS.md` D010–D013.
- **Failure handling (D066) — this was never decided, not just implemented wrong.** Feature 1 has an explicit fallback rule for API failure (§7: a plain, deterministic, non-AI-badged summary of the same structured figures). Feature 2 has no deterministic equivalent to fall back to — there is no template for "what the user meant" the way there's a template for "what the engine already computed" — so this boundary spec never said what should happen on an interpret-time failure, and the gap surfaced live as a raw provider error string ("Gemini API returned 429") reaching the user directly. The rule, now explicit:
  - **Never surface a raw API error, HTTP status code, or provider name to the user, under any circumstance.** `WhatIfPanel.tsx`'s `sendUtterance()` catch block previously did `err instanceof WhatIfError ? err.message : '...'` — and `interpretWhatIfTurn()` wraps a genuine fetch/provider failure into a `WhatIfError` whose message *is* the raw underlying text, so that branch was the direct cause of the leak. The fix: this specific catch (interpret-time only) never reads `err.message` at all — always a fixed, generic, honest string, regardless of the error's shape or origin. This is *not* the same call site as `handleConfirm()`'s catch, where a `WhatIfError` is guaranteed to be a safe, already-user-facing validation message (`confirmWhatIfCandidate()` makes no network call at all) — that site's existing `err.message` display stays as is, correctly.
  - **The message is honest that something went wrong and that it's temporary, with zero technical detail**: *"The Scenario assistant couldn't process that just now — this is usually temporary."*
  - **It reminds the user the manual path remains available** — Edit scenario / Add scenario — in the same message, not a separate one, since a failure state is exactly when the assistant being "an additional, equivalent edit tool, not the only one" (§8, D006/D007) actually matters to the person hitting it.
  - **Decided: in-panel Retry, not "just re-type it."** The failed utterance is already fully known (the user typed it, it's already rendered in the message list above the error) — making them retype it is pure friction for zero benefit, and the failure is presumptively transient (network/rate-limit/provider-side), so a Retry button that resends the exact same utterance through the exact same `sendUtterance()` path is both the lower-friction choice and the technically simpler one (no new state, just reuse what's already in scope). Implemented as an optional `retryUtterance` field on the error message variant, rendered as a button only when the interpret-time catch set it (never for a refusal, never for a business-rule error — those aren't retryable in any useful sense).

## 10. Working process — standing rules

- **Tooling** (source: `DECISIONS.md` D025, reconciled against the original pipeline's `ai_pipeline.html` tool-by-role inventory): kept and extended — Vitest, Playwright, Vercel/GitHub Actions. Dropped for this project — multi-model reconciliation (ChatGPT/Gemini comparison), Whimsical, v0, Jira/Atlassian Rovo; none serve a function this project's scope and scale actually needs (no open structural exploration, no multi-person coordination). Notion shifts to reference-only — no new pages authored here; new PM-lens decisions go into `DECISIONS.md` instead.
- **Verify, don't assume, whenever a specific fact matters.** This project's own history has repeatedly found live sources disagreeing with cached ones (see §11) — treat any UI copy, field behavior, or figure as unconfirmed until checked against the live app or the most current fetched source, not the first document that surfaces it.
- **Live source beats Notion/doc source when they conflict.** Track record on this project specifically: Notion and legacy `CLAUDE.md` files have drifted from shipped reality multiple times; the live app and current canonical HTML have not yet been found wrong.
- **Pull design tokens individually, on demand, not wholesale.** Do not embed PDB 05's full token/typography table into this file preemptively — that reintroduces the fragmentation problem this file exists to avoid, at the cost of bloating the one document meant to stay fully readable every session.
- **For any new visual element**: check PDB 05 / the design-system spec and the live previous-project app first. Only fall back to `pd/reference-screenshots/` (real Vanguard.com screenshots) as inspiration, not as a source of truth for this project's implementation — those screenshots were themselves just an input to the original design-system creation process, not a spec for what we're extending.
- **Log every decision to `DECISIONS.md` before ending a session**, tagged by role-lens (PM/PD/Dev). This is not optional bookkeeping — see §0.
- **A passing local check is only evidence about the runtime it actually exercises (D118).** `tsc --noEmit`, Vitest, and the Vite dev server all passed on code that broke in real production with `ERR_MODULE_NOT_FOUND`, because none of them use Node's native ESM module resolution the way Vercel's serverless runtime does — the main tsconfig's `moduleResolution: "bundler"` is deliberately lenient about exactly the thing that failed. When a fix targets a specific deployment/runtime environment, verify against something that actually exercises that environment's real constraints (here: real `esbuild` transpilation to genuine `.js` output + Node's actual `import()` resolver, once `vercel dev`'s own interactive-auth requirement ruled it out) — not just against whichever checks happen to already exist and already passed on the broken code.
- **Source control (D116/D117): commit as you go, not in large retroactive batches.** Each decision, or a small cluster of closely-related ones, should become its own commit at the time it's made — not accumulated for later reconstruction. D116 had to reorganize months of uncommitted work into a reviewable history and ran into real, tangled code dependencies that weren't visible until separation was actually attempted (a type produced by the engine, consumed across three different feature areas; a dialog component imported by pages in two different areas) — committing incrementally avoids that problem entirely, since each commit only ever needs to build against what already exists. Commit messages should cite the `DECISIONS.md` entries they correspond to, the convention already used for D116/D117 — keep the git log and the decision log cross-referenceable in both directions. Local commits don't need individual confirmation (fully reversible, no exposure risk); pushes do, but confirmation can be batched once per session or natural checkpoint rather than once per push. **Before every push**, a lightweight credential check — not a full historical re-audit, just confirming `.env.local` remains untracked and scanning what's actually about to go out for anything key-shaped. **Never force-push. Never delete a branch without first confirming its commits are reachable elsewhere** (merged, or present on another branch/remote) — a direct lesson from a near-miss during D116's commit reorganization (a branch holding real, otherwise-unrecovered work was deleted before its commits were confirmed reachable elsewhere; recovered via the retained SHA before any garbage collection risk, but worth stating explicitly rather than relying on general care next time).

Both were false-negative bugs in the *application's* handling of an otherwise-correct model response, not the model failing to understand the user's amount (which it got right every time, in the summary text and in the fund's own `sell_amount`, even on the calls that exhibited both failures) — confirmed by inspecting the real outgoing request payload first (per the task's own investigation order), which always contained the stated dollar amount correctly formatted. Fixed at the two points that actually own each concern: `whatIfResponseParser.ts` normalizes (b) at the structural-parsing boundary; `whatIfValidation.ts`'s `validateCandidate()` no longer requires `targetSaleAmount` unconditionally, only for `automated` mode, fixing (a) — manual mode's own per-fund `sell_amount` checks (already present) are sufficient on their own, and `whatIfCandidateToParams.ts` now derives `OptimizationParams.targetSaleAmount` from the fund selections' real sum rather than trusting a candidate field that can legitimately be absent. New tests in `whatIf.test.ts` use the exact real candidate shapes captured live from genuine API responses, not hypothetical ones.

## 13. Conditional-formatting rules register (D080 — traced fresh from code, not assumed; investigation/documentation only, no behavior changed)

Written ahead of the upcoming Traditional IRA banner redesign, which will touch displays that already use conditional coloring. There are three genuinely distinct rules in play, not one — conflating them in the new banner risks a real regression. Each was traced to its actual implementation, not inferred from the other two.

- **Rule 1 — Gain/loss figures (Est. ST/LT gains), sign-based, three states.** `stg > 0 ? green('#007a00') : stg < 0 ? red('#c8102e') : neutral(gray/ink)`. Confirmed identical across all four real locations that render a per-fund ST/LT gain figure: `ScenarioAnalysis.tsx` (`stColor`/`ltColor`, lines ~369–370), `FundSelectionManualLot.tsx` (both the summary-row builder around line 765 and the live-calc block around line 1040), `FundSelectionManual2.tsx` (`estSTColor`/`estLTColor`, lines ~392–394). A genuine third state exists at exactly zero (neutral, not colored either direction) — not a simple positive/negative binary. `ScenarioAnalysis.tsx`'s tax-summary `TaxRow` for "ST Capital Gains" (line ~397) applies the same green-on-positive convention at the aggregate level too.
- **Rule 2 — Per-fund allocation IMPACT badge (Stocks/Bonds/Reserves % change shown next to a single fund), sign-based on the raw delta — confirmed NOT toward/away-from-target, refuting this file's own prior assumption before this trace.** `fr.impact_pct <= 0 ? green : red`, identical across `FundSelectionAutomated.tsx` (line ~443), `FundSelectionManual2.tsx` (`impactColor`, line ~397), `FundSelectionManualLot.tsx` (line ~772). `impact_pct` itself (`buildFundResult()`, `dev/src/engine/index.ts`, `impactDelta` around line 346) is computed as `afterPct − beforePct` — the asset class's allocation share before vs. after this one sale — with **no target percentage anywhere in that computation**. So the color is a fixed convention (reducing a fund's own asset-class share is always shown green, increasing it is always shown red), not a comparison against `target_allocation`; a fund whose asset class is currently *under*-weight would still show red for a sale that increases it further toward target, and green for one that decreases it further away from target. Do not port a toward/away-from-target framing onto this figure specifically — it isn't one, whatever the visual similarity to Rule 3 suggests. **This is a real, user-facing misleading-display gap, tracked in §5's Business logic constraints (D080) alongside the other "flagged, not fixed" items** — a sale that deepens an already-underweight class's underweight can still render green.
- **Rule 3 — "Gap to target" rows (Scenario Analysis asset-mix impact table), magnitude-based, independent of sign.** `diffColor(diff)` (`ScenarioAnalysis.tsx`, line ~141): `Math.abs(diff) >= 0.5 ? red : neutral(black, '#040505')` — there is no green state in this rule at all, only red-if-material vs. plain-black-if-immaterial, and the ≥0.5 threshold is a percentage-point magnitude cutoff, not a dollar or sign threshold. Applied to all three asset classes (Stocks/Bonds/Reserves gap rows, lines ~454–456) via the one shared `diffColor()` function — confirmed genuinely shared, not per-class-duplicated logic that happens to match.

These three rules are independent and must not be assumed to generalize to one another: Rule 1 rewards positive vs. negative economically (a gain is good, colored green), Rule 2 rewards a *decrease* in a fund's own allocation share regardless of target direction, and Rule 3 rewards *smallness of gap* regardless of sign, with no green state at all. Any new IRA-banner display reusing one of these visual conventions must pick deliberately from this list, not copy whichever one looks visually closest.
