Vanguard AI-Enabled Sell & Rebalance

Project progress

Adds an embedded AI interpretive/generative layer — narration and a conversational what-if assistant — onto an existing, previously-built Vanguard Sell & Rebalance rebalancing tool. The application logic isn't changing; what's new is the AI layer that sits on top of it.

Last generated 2026-09-03

Feature status

Feature 1 Complete

AI narration layer, live at all four existing static-text touchpoints: Fund Selection rationale, Scenario Analysis tradeoff summary, Order Confirmation summary, and Execution Summary narrative.

  • Provider-agnostic architecture — a shared NarrationGenerator interface with a swappable implementation, not tied to one vendor. Three adapters exist and are tested in code (Gemini, Anthropic, Groq); the live Demo Settings dialog currently offers Gemini and Groq only, since this deployment has no configured Anthropic key.
  • Reader-tone segment (A–D) is user-selectable via Demo Settings, not hardcoded. Segments C and D's tone content, found cross-wired relative to their real personas, is corrected and sourced from the same real segment-research module Feature 2 uses; both segments' corrected content are now live-verified against real model output — Segment C (three real calls) and Segment D (five real calls across all four narration touchpoints), which also caught Segment D's own real consistency gap: the same shared "orient before stating specifics" rule was honored at some touchpoints and not others, traced to a real research field that existed but had never actually been used in the prompt.
  • Traditional IRA narration states the real computed ordinary-income tax figure (not just the qualitative rule) and correctly omits the early-withdrawal penalty entirely unless it's ever genuinely nonzero — never a reassuring aside filling the silence.
  • "Breakdown ▾"/"Why? ▾" progressive-disclosure controls on every real tax-figure touchpoint show the engine's actual blended-rate attribution, not a naive re-derivation — closing a real, previously-flagged compliance gap (no control existed for "how was this calculated," even though the figures themselves were always visible).
  • Deterministic text fallback if the live API call fails — never silently blank, never mislabeled as AI-generated.
  • Correct prospective/past tense per touchpoint (proposed sales narrated as "would realize," executed sales as "realized") — a real tense bug found and fixed after shipping.

Feature 2 Complete

AI-assisted "what-if" exploration — a "Scenario assistant" reachable both from Scenario Analysis's own header button and, now, directly from Fund Selection before an amount is even entered, opening the same drawer with an in-panel segmented control ("New" plus one option per existing scenario) for natural-language scenario building and editing.

  • Interpret → clarify → confirm loop: the engine is only ever called after the user confirms a plain-language interpretation of their request — no numeric preview exists before that point.
  • Real reader-segment tone (built fresh from the same segment-research module as Feature 1) and runtime-switchable provider selection, both driven by the Demo Settings dialog rather than a hardcoded default.
  • Calls the same calculation engine Fund Selection already uses, directly — no reimplementation of tax/lot logic. Code-level validators (not just prompt instructions) enforce SpecID-unavailable-on-Traditional-IRA, amount-can't-exceed-balance, and that a pre-confirm summary can never leak a computed tax/gain figure before any calculation has run.
  • Can create a new scenario, modify an existing one in place, or build a new scenario from an existing one as reference ("like Scenario 1 but...") — including a cross-account reference ("...but in my Roth IRA"), which correctly grounds any fund/lot in the target account's own real holdings rather than the referenced scenario's.
  • A new entry point on Fund Selection — a bordered banner, styled to a real mockup, visible only while nothing has been specified yet — lets a user skip straight to describing what they want instead of filling in the amount form first. Reaching this newly-exposed path also surfaced and fixed two real pre-existing bugs in how Scenario Analysis seeds its own demo data (see Highlights).
  • Closing the assistant panel mid-conversation now asks for confirmation before discarding an unconfirmed request — it used to happen silently.
  • A two-tone "AI-assisted — [Custom/priority]" badge discloses provenance, sharing the existing scenario badge's pill rather than stacking a second one.

Highlights worth knowing at a glance

Engineering findings — bugs caught, code-level guarantees built, things verified rather than assumed.

A "verified live" claim that hadn't actually visited the real front door

A new entry point into the Scenario assistant was added to Fund Selection, verified live, and reported working — but the verification had only ever navigated directly to the internal /automated route, never the app's actual root landing page, a genuinely separate component with its own copy and its own button ("Get recommendation," not "Calculate") that the original self-audit had conflated with the page it did check. A user starting from the real front door saw no banner at all. Found by treating a follow-up "this doesn't match what I'm seeing" report as ground truth over the prior write-up, then tracing the actual rendered component tree rather than re-trusting the first pass.

A second "it's fixed" claim, undone by Vite's own hot-reload behavior

A real bug — Scenario Analysis silently re-populating 3 demo scenarios after they'd been explicitly deleted — was fixed and verified live. A follow-up report said the fix had made things worse, reseeding "regardless of navigation." Direct state tracing (a temporary debug hook reading the store's real values at every step) showed the fix was correct the whole time — real in-app navigation never re-triggered it. The actual cause: the store module had no Vite HMR boundary of its own, so every further code edit silently re-created it from scratch, with no "page reload" line in the dev log to hint why. Fixed by making the store a genuine HMR self-accept boundary — a fix that also protects every other piece of in-memory session state from the same silent reset, not just the one field that happened to expose it.

A third real gap, found only because the check didn't stop at the two reported examples

Segment D's narration is supposed to orient the reader before naming a specific fund and dollar figure. Reading real generated output cold showed it doing that correctly at Scenario Analysis but not at Fund Selection's per-fund rows — the two touchpoints originally reported. Checking the other two touchpoints anyway (not assumed fine) found Order Confirmation already correct, but Execution Summary silently sharing the same gap as Fund Selection — a third, previously unflagged case. The actual cause: a real research field naming this exact requirement ("orientation before action") had existed since the segment's content was first corrected, but was never actually referenced in the prompt text — only two of its three fields were. Fixed by using it, verified with five fresh real model calls read cold, not just a structural check that the new rule text exists.

Real dollars, not just a rule, for Traditional IRA narration

Traditional IRA narration used to state only the qualitative rule — "taxed as ordinary income, regardless of this gain/loss figure" — because there was no real computed figure to state until a separate piece of work made that number real. Once it existed, narration was updated to state it plainly ("...an estimated $2,400.00 in this case"), live-verified against a genuine model call. Along the way, a second, unrelated gap turned up: Manual mode's per-fund narration was never even passed the aggregate tax figure at all, so it silently couldn't state one for any account type — fixed in the same pass rather than left for later.

A provider-failure indicator that refuses to guess

When a live AI call fails, a real HTTP 429 is a reliable "you've hit a usage limit" signal — already seen twice for real in this project. Anything else (a bad key, a network failure, a malformed request) isn't, and the indicator now added to Demo Settings says so honestly: specific wording only for a confirmed 429, generic wording otherwise, never a guess dressed up as a diagnosis. A follow-up pass found the display was missing its date (a bare time alone misreads as "this morning" if ever seen the next day) — fixed, and the underlying assumption that a stale message could never actually render was itself checked rather than taken on faith (see "What's not built yet" below for the one narrow gap that check surfaced).

A validator that caught its own designer's mistakes twice before shipping

Building a code-level check for "never state a computed tax figure before confirming" sounds simple until it meets a real fund name: the first draft flagged every summary mentioning "MinTax" as if it said "tax." The fixed version then flagged a genuinely correct request ("optimizing for the lowest tax impact") as if that were a computed estimate too. Both were caught by the test suite's own first run, before either version reached the live app.

A four-year-old-looking bug that had never once been tested

Two of narration's four reader-tone variants — the ones for a stressed, time-pressured reader and a reader who's new to investing — had their actual defining traits swapped: the "explain everything in plain language" content sat on the wrong one, and the "get to the point fast" reader was getting a slower, more explanatory tone instead. It went unnoticed because neither variant had ever been generated, tested, or reviewed even once since the day it was written.

Multi-account scenarios: investigated, then actually designed for

A live test confirmed a real user can build one scenario against Taxable Brokerage and another against Traditional IRA, coexisting in the same comparison — each computed correctly, but the page's single account label could misattribute an older scenario. That finding is now closed: each scenario shows its own account on its own column, and the assistant's panel shows a summary card confirming which account and scenario it's currently touching.

Account switching: real, and it found a systemic bug

Enabling the previously-decorative Taxable/Traditional IRA/Roth IRA account selector was the first time a non-taxable account was reachable at all — which surfaced a pre-existing, project-wide bug: ~10 call sites across 5 files computed capital-gains tax unconditionally, with no gate on account type. Found and fixed, with the gate now a documented required pattern for any new tax computation.

Design lessons

This project's stated primary purpose is learning to design AI-enabled applications, not just build them — so what changed in how AI-enabled products should be designed matters as much as what was fixed in code. These are distinct from the engineering findings above, not a restatement of the bug each one happened to surface alongside.

Lesson 1

Free-text testing has no natural stopping point. The fix, applied to the Scenario assistant's multi-lot selection feature, was enumerating real axes of variation (fund count, account type, cost-basis method, how an amount is specified, ambiguity level) and confirming every meaningful combination was covered — a specific, finite check, not indefinite trial and error.

Lesson 2

Testing whether the assistant could select funds by "smallest embedded gain," an $8,000 test case happened to pick the same fund the system's unrelated default tax-optimization method would have picked anyway — so a correct answer couldn't prove the instruction was actually followed rather than ignored. A $30,000 case that forced a real multi-fund split was the one that actually proved the capability.

Lesson 3

Researching SEC guidance on investment advice showed the real line isn't "no algorithmic recommendations" — this app's existing tax-optimization recommendation already is one. The line is adding a new, generative, forward-looking layer of directive language on top of an already-deterministic recommendation, which is what the narration and assistant features were deliberately designed never to do.

Lesson 4

Because the narration layer was never allowed to influence a computed tax or gain figure, two later features — letting a demo viewer preview different tone styles, and switching between Gemini/Groq/Anthropic — both worked cheaply, needing only new adapters, because neither one risked touching the numbers underneath.

Lesson 5

This project's own user-research documentation explicitly warned that a proxy signal like login count doesn't reliably indicate someone's actual situation. The same risk applied to inferring an investor's persona from which mode or cost-basis method they picked — so an explicit, honest "preview as" control was built instead of a confident-but-likely-wrong automatic classifier.

Lesson 6

A user-research note said one investor persona should avoid unnecessary complexity, like comparing scenarios. Read literally, that could have meant hiding the Scenario Analysis feature for that persona entirely — a much stronger and riskier move than what the research actually intended, which was about not proactively pushing it as a default, not removing it as an option.

Lesson 7

The per-fund "Impact" badge on Fund Selection was assumed to be colored based on whether a trade moves an allocation toward or away from its target — a reasonable-sounding guess. When actually traced in the code, it turned out to be a fixed rule based only on the sign of the raw change, with no target percentage anywhere in the calculation. That means a Manual-mode sale that makes an already-underweight position even more underweight could still show a green badge. The catch mattered because the wrong assumption was about to be relied on while designing the new IRA summary banner — verifying it first meant that design never got built on a false premise.

Lesson 8

Mapping this project's two features against roughly a dozen real AI-industry patterns — including ones deliberately not used, like retrieval-augmented generation, multi-agent systems, and autonomous execution — and being able to explain why each one was or wasn't the right fit is itself evidence of design judgment, separate from the two features actually built.

Lesson 9

Two separate "verified live" reports — a UI banner and a scenario-seeding fix — each turned out not to match what an independent, direct look actually showed, in a live-editing dev environment where hot-reload activity happens constantly between one check and the next. The fix in both cases wasn't a better screenshot; it was tracing the actual mechanism (which component tree really rendered, what the real store state was at each step) rather than re-trusting an earlier, plausible-looking pass. A live check is only as strong as what it actually exercised — which page, which navigation path, which moment relative to the last edit — not just that something rendered correctly once.

Improvements to the underlying application

Not every fix made during this project was about AI. Several of the most consequential ones are corrections to the base Sell & Rebalance application itself — defects that predate this project, several never even reachable until AI-related work (mainly getting account switching genuinely working, so Feature 2 could reach every account type) was the first thing to actually exercise the code path that had been broken. A real, complementary outcome of the work, not the primary objective — but the underlying application is genuinely more correct today because of it.

Account switching

  • The account-type selector was never functional in the original application — no click handler existed anywhere, in either mode; wired up for the first time.
  • Once wired up, it revealed the app had been silently fabricating tax figures for non-taxable accounts — roughly ten independent call sites computed capital-gains tax unconditionally with no account-type check — a live Roth IRA run showed a fabricated $1,818.30 "EST. NET TAX" and a fabricated "you saved $1,090.98" banner on an account that owes no capital-gains tax under any method.
  • Two layout-coherence bugs surfaced alongside it — a fixed-position fund table could show one account's holdings under a different account's heading, and the account list visually reordered itself on every switch instead of holding still.
  • An engine gap: a budget-splitting sale calculation could silently drop part of a requested amount — an account with only one qualifying holding left part of the target unsold with no error or warning — a $25,000 request against a single-holding Roth IRA silently returned only $15,000.
  • Stale account data could carry over when switching accounts inside Manual mode — a React state bug unrelated to anything AI-related: manual-session selections keyed only by fund ticker bled from one account into another, breaking the very next Manual-mode visit.
  • A third, distinct Manual-mode bug: the sell amount could vanish entirely — switching directly between two non-taxable accounts while already in Manual mode hit a stale-closure trap, computing against the previous account's id even after the store had already updated.
  • A dev-only masking issue — a React behavior specific to development mode was silently recovering from a real bug that would have shown stale, wrong-account figures with no recovery path in an actual production build.
  • "Edit scenario" never restored which account a saved scenario belonged to — clicking Edit on a scenario built against one account could silently show a freshly-computed, completely different account's recommendation instead of the actual saved data.

Tax accuracy

  • Traditional IRA withdrawals were never actually taxed as ordinary income anywhere in the app — silently treated as tax-free, identical to a Roth IRA; implemented for real, consolidated into one shared calculation used by both Automated and Manual mode, then the display layer redesigned to match across all six real summary touchpoints.
  • The tax bracket "Change" control was planned in the original project but never built — implemented for the first time, using real, accurate 2026 federal tax bracket data across all three real filing statuses.

Display correctness

  • Order Confirmation had an internally inconsistent account-type display — correct in one section of the page, hardcoded to the wrong literal word in another section of the same page.
  • Execution Summary never correctly displayed which account a transaction was for — its one account mention always showed the same generic, incorrect label regardless of the real account type.
  • A footer button-alignment inconsistency between Automated and Manual mode, present since the original project, was corrected — Manual mode's own reset/action buttons were left-justified together instead of matching the reset-left, actions-right pattern every other footer in the app already used.
  • A layout bug caused fund-row content to overlap adjacent elements in Manual mode — a fixed-height container sized for old, short placeholder text cut real content off mid-word once it grew longer than the container had ever anticipated.
